# 死代码分诊（Audit Dead Code）

本项目有大量 dead code，分两类：**真死**（编译期零引用）与**逻辑死**（有引用但没有任何真实用户路径触达它）。后者更危险——它看起来活着，会诱导人在其上叠加新代码。加上**预留**类（架构意图明确但尚未接线），共三类。本 skill 给出统一的发现与分诊流程。

**为什么会积累这么多**：架构走了三轮（自研 → 模仿/重写 pi + 参考 kimi-code → 重构），每轮都留了「以后再接」的骨架。骨架没被真实入口驱动，就成了逻辑死码；为让它过编译又加了大量 `#[allow(dead_code)]`，把问题藏起来。

## 1. 发现

按范围从窄到宽跑：

```bash
# (a) 被显式压制的死码 —— 最可疑，是逻辑死的高发区
rg -n '#\[allow\(dead_code\)\]' src --type rust

# (b) 编译期真死（临时去掉所有 allow，让编译器全量报）
#     操作：把 src/lib.rs 顶加 #![deny(dead_code)] 临时编译，记下全部 dead_code 告警，再撤回。
#     （不要提交这次临时改动。）

# (c) 引用图：某个 pub 项到底有没有真实调用方
rg -n '<符号名>' src tests --type rust   # 看调用点是否只在定义文件 / cfg(test) / doc 注释里

# (d) feature-gated 死码：某 feature 下的代码有没有 feature 外的消费者
rg -n 'cfg\(feature\s*=\s*"server"\)' src --type rust   # 换 server/tui/rpc/gui 逐个查
```

对 (a)，逐条看它压制的符号，按第 2 节归类。**`#[allow(dead_code)]` 本身不是结论**——它只标记「这里有人觉得它暂时没用」，是分诊起点。

## 2. 三类分诊

| 类别 | 判据 | 处置 |
|---|---|---|
| **真死** | 编译期零引用（含 `pub` 但无外部消费者；或私有且模块内无调用） | 删。无例外 |
| **逻辑死** | 有引用，但引用方本身也未被任何真实入口（`main.rs → lib::run → app::cli::run` 链）触达；或引用方是死代码 / `cfg(test)` / doc 示例 | 逐个决定：能被某新面在**本变更内**驱动 → 激活并去掉 `#[allow(dead_code)]`；否则 → 删。绝不在其上叠加新代码 |
| **预留** | 架构意图明确（如 `RemoteDriver` 服务于未来的 server 客户端、`Driver` trait 为多面设计），且近期有落地计划 | 保留，但在符号上方注释说明「为哪个变更/面预留」+ 预期落地条件。若 6 个月内无落地迹象，降级为真死删除 |

判定「真实入口触达」的方法：从 `src/main.rs` 出发，沿 `app::cli::run` 的实际分支（当前只有 print 模式 + `--rpc` + 子命令）追调用链。触达不到的，即使 `pub`、即使被 `cfg(test)` 引用，都是逻辑死。

## 3. 本仓库已知的逻辑死热点

基于历次扫描事实汇总；复核以 `rg` 实时结果为准。

| 区域 | 现状 | 初判 |
|---|---|---|
| `app/core/driver.rs::RemoteDriver` | 完整实现，全仓库零实例化 | 预留（server 客户端面落地时激活；见 `write-surface`） |
| `app/gui.rs` + `gui` feature | 3 行空占位，feature 编译不出任何东西 | 真死 → 删（除非本变更内就建 GUI 面） |
| `app/rpc.rs::Command` 全集（20 变体） | dispatch 多数有实现，但仓库内无 RPC 客户端消费 | 预留/逻辑死：interactive 面的 slash 命令应复用这套语义来激活它 |
| `#[allow(dead_code)]` 标记 | 见步骤 1(a)，逐条分诊；实时数量 `rg '#\[allow\(dead_code\)\]' src --type rust` | 多数为逻辑死，少数为预留；逐个审 |

> 这些是**起点清单**，不是结论。重做分诊时以第 1 节的实时扫描为准。

## 4. 处置动作

- **删**：直接删符号。若删后编译报 `unused import`，一并清。删 feature 时同步清 `Cargo.toml` 的 `[features]` 与依赖（如删 `gui` 连带无需的 GUI 依赖）。
- **激活**：在真实入口接上线（如把某个 `Command` 变体挂到 interactive 面的 slash 处理），并**去掉** `#[allow(dead_code)]`。激活后该符号必须被真实路径触达，否则没真正激活。
- **保留（预留）**：在符号正上方加一行注释：`// 预留：<变更/面>；落地条件：<…>；否则 c<NNN> 后降级删除`。

## 5. 红线

- 用「加 `#[allow(dead_code)]`」来解决「新建的骨架暂时没人用」。骨架要进仓库，必须同变更内有真实入口驱动。
- 分诊时只看「定义文件内是否被引用」——必须追到真实入口链。
- 删「预留」类时不看注释里的落地计划——预留类的删降级以注释为准，先确认计划是否过期。
- 把「逻辑死」当成「预留」长期留着。逻辑死的默认处置是删，只有明确的近期计划才升为预留。

## 6. 与 SDD 的衔接

死代码分诊的结论应写进相关变更的 `design.md`（「清理范围」一节）或新建一个 `c<NNN>-audit-dead-code-*` 变更。分诊不是游离于 SDD 之外的随手清理——删/激活都要落到 specs/tasks 上。
