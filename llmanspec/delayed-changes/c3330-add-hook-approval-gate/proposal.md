# 钩子与可执行配置的逐项审批门

> **⚠️ deferred（2026-11-11）**：源自 c3235 深挖对齐（用户判断：项目信任与工具信任应分层可控、且控制权不得被恶意插件/hook 篡改）。本期 c3235 仅移除未接线的 requires_approval 死字段；本 change 后置，启动时经 propose 迁回 changes/。

## Why

hooks 的 command 本身就是任意命令执行；外进程插件同理。当前只有一道项目级粗闸：trust 门禁决定项目 config（含项目层 hooks）是否加载——信任一次，其全部 hooks 即获得执行面，用户没有逐项控制权。历史上 requires_approval 字段是此设想的半截实现，全仓零读取，已在 c3235 移除（分析见 c3235 research/requires_approval-followup.md）。

用户诉求（2026-11-11 对齐原话归纳）：

1. 项目信任 ≠ 工具信任：信任一个项目干活，不等于授权它配置里的每条 hook / 插件执行任意命令。
2. 控制权必须分层给出：资源加载（项目 config）、可执行配置装配（hooks / 外进程插件）、运行时权限（工具执行）三层各自独立可控。
3. 审批状态不得被其管制对象篡改：恶意 hook / 插件不能自动同意自己、不能静默改写审批记录。

## What Changes（预期目标）

- 用户级审批注册表：存用户目录（~/.xylitol 下、项目目录不可达），条目 = 可执行配置指纹（command 串 + 事件模式 / 插件 manifest 哈希）→ 允许 / 拒绝。
- 加载期审批：未批准的可执行配置在装配前弹出审批（仅经产品端 TUI / CLI 交互，不提供编程接口）；拒绝 = 不装配 + 启动诊断可见。
- 变更即失效：指纹变化（改命令、改事件、换 manifest）视为新条目，须重批。
- 覆盖面分阶段：第一版项目层 hooks；第二版外进程插件（trusted: true 现在只是配置声明，升级为用户审批）；MCP server 命令可选纳入。
- 审计与篡改检测：审批动作 append 审计链（时间、指纹、来源 config 路径）；启动时校验注册表与审计链一致性，不一致 = 视为全部未批 + 醒目告警。
- 防篡改策略分层（诚实边界：与用户同权限的恶意代码在原理上可伪造一切本地状态；目标是「项目层不可篡改 + 同权限篡改可检测 + 审批动作不可自动化」三层缓解）。

## 启动时机

- 当前批次（c3230-c3325 状态机修复）完成后排期；不晚于 hooks / 插件配置可分享、模板化或市场分发落地之前。
- 依赖：c3235 已落地（失败语义与死字段清理完成，审批门不与 fail-closed 语义纠缠）。

## Capabilities

- domain-security（trust / 审批工作流）；agent-hooks（装配期）；infra-plugin（外进程插件第二版）。

## Impact

- 新增用户级审批状态与交互；不改 hook 执行协议（stdin/stdout JSON 不变）。
- 与 trust 门禁关系明确化：项目信任 = 允许加载资源；本门 = 允许装配可执行配置；两层不合并。
