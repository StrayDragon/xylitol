# Design: c2951

## 1. 为什么这算「合约」而不是「实现细节」

预演本身是 c2945 的实现手段（为了拿到最终工具名重算权限与并发窗）。但它的副作用是**插件可观察的**：

```text
批内调用 [A, B]
→ 预演 A：hooks → AgentHooks → middleware.before_tool
   A 的中间件返回 stop  ⇒ stop_run
→ 预演 B：hooks → AgentHooks → middleware.before_tool   ← B 的中间件仍然运行
→ 执行阶段：A 记 tool-error；B 因 stop_run 不执行（无 ToolExecutionStart/End）
```

插件若在 `before_tool` 里做审计计数、资源预留、幂等标记，就会看到「我运行了但工具没跑」。这必须写进合约，否则插件作者只能靠读 design（会进 archive）猜。

## 2. 合约措辞

在 `r2922` 现有句子之后追加一段，不改既有条款语义：

> 预演 须先于本批任何工具执行完成；批内前序调用返回 stop 时，后续调用的中间件 已运行 但其工具 不得执行，中间件 不得假设「放行即执行」。

用「已运行」而非「可能运行」，因为实现是确定性的整批预演。用「不得假设」而非「须感知」——不给中间件额外输入，只约束其推断。

## 3. 场景设计

一个场景即可钉住两件事（后者运行过、后者工具没执行）：

```gherkin
场景: 前序停止后批内中间件已运行
  假如 注册两个 before_tool 中间件且首个对第一调用返回 stop
  当 运行 AgentRuntime 触发两个工具调用
  那么 第二个中间件已被调用且其工具未执行
```

步骤实现需要「第二个中间件被调用」的可观测位。用与既有 `Scripted` 同形的中间件，加一个共享计数（`Arc<AtomicUsize>`）在 `before_tool` 里自增；断言计数 ≥ 2（第一个中间件 + 第二个中间件各一次），且事件流里只有第一个调用的 `ToolExecutionStart`。

## 4. 为什么不做回滚 / dry-run

让中间件「预知本批是否会被中断」需要二次调用或事务性批执行，代价远大于收益：中间件本来就应写成「放行只是必要条件，不是充分条件」。本 change 只做**如实声明**。

## 5. 代码改动

无。现有 `prepare_call` 整批先行、`stop_run` 逐调用传播已符合该语义；本 change 是 spec + BDD + 一行 AGENTS 补充。
