# BDD-on 迁移试点:验证 solidify → bdd.rs 新链路可行性

## 背景与核心矛盾(源码确认)

经 llman 0.0.61 源码分析,本项目存在**两套并行的 BDD 系统**:

| 维度 | 旧系统(当前 bdd.rs) | 新系统(0.0.61 BDD-on) |
|---|---|---|
| feature 路径 | `tests/features/<x>.feature`(手写) | `llmanspec/specs/<cap>/<cap>.feature`(solidify 生成) |
| 场景标题 | 中文语句("三层配置合并") | `scenario.id` 英文 kebab("parse-list") |
| SSOT | feature 文件本身 | `spec.toon` 的 scenarios |

**关键源码事实**(支撑决策):
- solidify 写入路径**硬编码** `llmanspec/specs/<cap>/<cap>.feature`(`src/sdd/solidify.rs:184-188`),**不读 config.feature_dir**
- 场景标题 = `scenario.id.trim()`(`solidify.rs:203`),rstest-bdd 的 `#[scenario(name=...)]` 需字节级匹配
- `config.feature_dir` 字段**运行时不被读取**(仅模板渲染用),所以 config 里写 `tests/features` 不影响 validate
- validate full mode 跑整个 `cargo test --test bdd`(batch),不区分单 feature
- `strip_quotes()` helper**已存在**(`bdd.rs:193`),引号陷阱已处理

## 试点目标

**不是**迁移现有 feature,而是**验证 solidify 生成 → bdd.rs 消费这条新链路本身在本仓库能跑通**。验证通过后再决定是否全量迁移(109 场景)。这是风险最低、信息量最大的试点。

## 试点选择:`agent-runtime` spec(已归档,无 delta 风险)

选 `agent-runtime`:
- spec.toon 有 25 个 scenarios,标题是英文 kebab(`react-terminates`、`stream-is-xyevent`)
- 已归档(不在 active changes 里),solidify 不会动它——但我们可以**手工对 main spec 跑一次 solidify 风格的生成**
- 现有 `agent.feature` 有 8 个中文标题场景且全绑定通过,**不冲突**(新链路用新路径)
- ReAct 循环/XyEvent 的 step 实现已大量存在于 bdd.rs

## 实施步骤

### 步骤 1:确认 solidify 对 main spec 的行为
- `agent-runtime` 是已归档 spec(无 delta)。solidify 只处理 change delta,对 main spec 无操作。
- 因此**手工模拟** solidify 产出:按 `solidify.rs` 的 `render_scenario` 规则,从 `agent-runtime/spec.toon` 的 25 个 scenarios 生成一个 `llmanspec/specs/agent-runtime/agent-runtime.feature`(标题=`id`,步骤从 given/when/then 映射)。
- 先用 `--dry-run` 在一个临时 change 上验证格式,或直接参照 `solidify.rs:201-235` 的规则手工产出一个最小子集(选 2-3 个 scenario,如 `react-terminates`、`stream-is-xyevent`)。

### 步骤 2:在 bdd.rs 新增新链路绑定
- 新增 `#[scenario(path = "llmanspec/specs/agent-runtime/agent-runtime.feature", name = "react-terminates")]` 等(标题用英文 id)
- 复用现有 step 函数(`#[given]/#[when]/#[then]`)——这些是**路径无关**的,只要步骤文本匹配即可
- 若步骤文本与 spec.toon 的 given/when/then 不匹配,微调 spec.toon 的字段文本(因为 spec.toon 是 SSOT,改它合理)或新增薄 step

### 步骤 3:跑通验证
- `cargo test --test bdd -- --test-threads=1` 确认新链路场景通过
- 旧 `tests/features/agent.feature` 绑定**保持不动**(双轨并存,试点期间)
- `llman sdd validate agent-runtime --check` 确认 llman 视角也通过

### 步骤 4:评估与决策
- 记录试点发现:格式映射是否顺滑、step 复用率、spec.toon 文本是否需调整
- 据此判断全量迁移的可行性(109 场景)与工作量,产出后续迁移计划

## 约束
- 只动:`llmanspec/specs/agent-runtime/`(新增 .feature)、`tests/bdd.rs`(新增少量绑定,可能微调 spec.toon 文本)。**不删**任何现有 `tests/features/` 文件或绑定(双轨并存)。
- 不改 config.yaml(`feature_dir` 已确认无效,不动)。
- 不动其它 spec / change / 源代码。
- 试点后若验证失败,回退本次改动即可,零副作用(旧链路未受影响)。

## 预期产出
1. 一个 solidify 风格生成的 `.feature`(`llmanspec/specs/agent-runtime/`)
2. bdd.rs 中 2-3 个新链路 scenario 绑定,全绿
3. 试点报告:新链路可行性结论 + 全量迁移建议(路线、工作量、风险)
